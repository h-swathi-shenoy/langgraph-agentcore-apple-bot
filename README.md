# Apple Support Bot — Intermediate LangGraph Agent with Multi-Turn Memory

A step up from the basic calculator example: this agent has **two tools**,
**multi-turn conversation continuity within a session**, and **long-term
memory that persists across separate sessions/days**, powered by Amazon
Bedrock AgentCore's native Memory service (no LangMem needed).

## What's different from the calculator agent?

| | Calculator agent (`../my-agent`) | Apple Support Bot (this folder) |
|---|---|---|
| Tools | 1 (calculator) | 2 (troubleshoot_lookup, order_warranty_lookup) |
| Conversation | Stateless — every call is independent | Multi-turn — remembers what you said earlier in the same session |
| Cross-session memory | None | Yes — recalls facts/preferences from previous, separate sessions |
| Memory resource | Auto-created `STM_ONLY` by `agentcore configure` | Manually provisioned with `SEMANTIC` + `USER_PREFERENCE` long-term strategies |

## Architecture

```
POST invoke {prompt, actor_id, session_id}
        │
        ▼
MemorySession (actor_id + session_id scoped)
        │
        ├─ 1. get_last_k_turns()          → short-term history (this session only)
        ├─ 2. process_turn_with_llm(...)  → retrieves relevant long-term memories
        │        │                          from OTHER sessions for this actor_id
        │        ▼
        │   llm_callback(user_input, memories)
        │        │
        │        ▼
        │   LangGraph ReAct loop (agent ⇄ tools ⇄ agent → END)
        │        │
        │        ▼
        │   final answer (string)
        │
        └─ 3. auto-saves this turn back to memory (both short-term event log
              and, asynchronously, extracted into long-term semantic/
              preference records for future sessions)
```

## Why `actor_id` and `session_id` matter

- **`session_id`** scopes *short-term* memory — the raw back-and-forth turns.
  Two calls with the same `session_id` will see each other's conversation
  history (e.g. "I already tried that" makes sense to the bot).
- **`actor_id`** scopes *long-term* memory — durable facts/preferences
  extracted from **all** of that actor's past sessions, regardless of
  `session_id`. This is what lets the bot recognize a returning user
  "tomorrow" in a brand-new session, as long as `actor_id` matches.
- Different `actor_id`s are fully isolated from each other (verified below).

In a real product, `actor_id` would be your authenticated user ID (not a
hardcoded test string), and `session_id` would typically be a new UUID per
conversation/tab, generated by your frontend.

## Tools

**`troubleshoot_lookup(issue_keyword)`** — mock knowledge base covering common
issues: `iphone battery`, `mac wont turn on`, `airpods not connecting`,
`ipad frozen`, `apple watch not charging`.

**`order_warranty_lookup(order_id)`** — mock order database. Valid test order
IDs: `W1234567890` (iPhone 15 Pro), `W1234567891` (MacBook Air M3, AppleCare+),
`W1234567892` (AirPods Pro 2). Computes warranty expiry and ACTIVE/EXPIRED
status (AppleCare+ doubles the coverage window in this mock).

**`update_order_applecare(order_id, has_applecare=True)`** — lets the agent
"add AppleCare+" to an order when a user says they just purchased it. Mutates
the same in-memory `_MOCK_ORDERS` dict that `order_warranty_lookup` reads from,
so a follow-up warranty check in the same conversation (or even a later,
separate `agentcore invoke`) can reflect the change — **but only if AWS happens
to route the request to the same warm container**. See the callout below.

### ⚠️ Known limitation: this "update" doesn't reliably persist

`_MOCK_ORDERS` is a plain Python dict living in the memory of **one running
container process**. AgentCore Runtime is serverless: it can spin up new
container instances on cold start, after idle periods, when scaling to handle
concurrent traffic, or on every redeploy. Each instance gets its own fresh copy
of `_MOCK_ORDERS` from the source code — so an update made on one instance is
invisible to another, and disappears entirely once that instance is recycled.

We verified this empirically: three consecutive `agentcore invoke` calls a few
seconds apart (check → update → check again) showed the AppleCare+ update
successfully persisting, because AgentCore reused the same warm container for
all three. But there's no guarantee of that — a cold start or a second
concurrent instance would silently revert to the hardcoded defaults.

**This is fine for a demo** (it's illustrating "agent calls a tool that
changes state"), but a real production version of this tool would need to read
and write an external store — e.g. DynamoDB — instead of an in-process dict,
so updates survive cold starts and are consistent across all instances. We
intentionally left this as in-memory for now; swap in DynamoDB (or your real
order-management backend) if you take this beyond a demo.

## Setup & Deploy — step by step

### 1. Install deps
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Grant the execution role Memory permissions
The shared `AgentCoreRuntimeRole` (from the calculator example) needs
additional permissions to create/read/write AgentCore Memory resources:
```bash
aws iam put-role-policy \
  --role-name AgentCoreRuntimeRole \
  --policy-name AgentCoreMemoryPermissions \
  --policy-document file://memory-permissions.json
```

### 3. Provision the Memory resource (one-time)
```bash
python3 create_memory.py
```
This creates a Memory resource with two **long-term** strategies:
- `semanticMemoryStrategy` → namespace `/support/facts/{actorId}/`
- `userPreferenceMemoryStrategy` → namespace `/support/preferences/{actorId}/`

Short-term event storage (raw turns) is included automatically with any
Memory resource. Copy the printed Memory ID — you'll need it in step 5.

### 4. Configure the agent
```bash
agentcore configure \
  --entrypoint app.py \
  --name apple_support_bot \
  --execution-role arn:aws:iam::<ACCOUNT_ID>:role/AgentCoreRuntimeRole \
  --requirements-file requirements.txt \
  --region us-east-1 \
  --disable-memory \
  --non-interactive
```
`--disable-memory` tells AgentCore *not* to auto-provision its own
`STM_ONLY` memory (like the calculator agent uses) — we're bringing our own
memory resource with long-term strategies instead, created in step 3.

### 5. Deploy, passing the memory ID as an env var
```bash
agentcore deploy --env APPLE_BOT_MEMORY_ID=<memory-id-from-step-3>
```
Our `app.py` reads `APPLE_BOT_MEMORY_ID` from the environment and connects
`MemorySessionManager` to that specific memory resource.

## Verified test sequence (real deployment)

```bash
# Turn 1 — new session, report an issue
agentcore invoke '{"prompt": "Hi, my iPhone battery drains really fast", "actor_id": "test-user-1", "session_id": "session-A"}'
# -> tool called (troubleshoot_lookup), gives battery health / iOS update / replacement steps

# Turn 2 — same session, follow-up (tests SHORT-TERM memory)
agentcore invoke '{"prompt": "I already checked battery health and its fine. What else can I try?", "actor_id": "test-user-1", "session_id": "session-A"}'
# -> understands "already checked" refers to turn 1, gives DIFFERENT next steps
#    (background app refresh, location services, low power mode, etc.)

# Turn 3 — same session, different tool
agentcore invoke '{"prompt": "Can you check the warranty on order W1234567891?", "actor_id": "test-user-1", "session_id": "session-A"}'
# -> tool called (order_warranty_lookup) -> "ACTIVE, expires 2026-11-02, AppleCare+: Yes"

# [wait ~60s for async long-term memory extraction]

# Turn 4 — BRAND NEW session (session-B), same actor (tests LONG-TERM memory)
agentcore invoke '{"prompt": "Hey, its me again. Did we figure out my earlier device issue?", "actor_id": "test-user-1", "session_id": "session-B-tomorrow"}'
# -> "long_term_memories_used": 5
# -> correctly continues the iPhone battery troubleshooting thread with NO
#    shared session_id — proves recall came from long-term memory, not
#    short-term session history

# Turn 5 — different actor entirely (tests ISOLATION)
agentcore invoke '{"prompt": "Hey, did we figure out my earlier device issue?", "actor_id": "different-user-2", "session_id": "session-X"}'
# -> "long_term_memories_used": 0
# -> "I don't have access to previous conversations" — correctly isolated
#    from test-user-1's history
```

## Response shape

```json
{
  "result": "<agent's final text answer>",
  "memory_enabled": true,
  "actor_id": "test-user-1",
  "session_id": "session-A",
  "long_term_memories_used": 5
}
```

## Gotcha we hit while building this

`process_turn_with_llm()`'s `llm_callback` **must return a plain `str`** —
but `ChatBedrock` message `.content` is sometimes a list of content blocks
(e.g. `reasoning_content` + `text` blocks) rather than a plain string, which
raised:
```
ValueError: LLM callback must return a string response
```
Fixed by adding a `_content_to_text()` normalizer that flattens either shape
(str or list-of-blocks) down to a single display string before returning it
from the callback. See `app.py`.

## Do you need LangMem for this?

No — this entire multi-turn + long-term-memory implementation uses only
`bedrock_agentcore.memory` (already bundled in the `bedrock-agentcore` SDK
you installed for the runtime itself). LangMem would only be worth adding if
you moved off AgentCore's managed Memory service entirely (e.g. self-hosting
LangGraph with your own Postgres-backed store) or needed memory extraction
logic AgentCore's built-in `semantic`/`userPreference`/`summary`/`episodic`
strategies don't cover.

## Cleanup

```bash
agentcore destroy
```
Then, if no longer needed, delete the memory resource and its extra IAM policy:
```bash
aws iam delete-role-policy --role-name AgentCoreRuntimeRole --policy-name AgentCoreMemoryPermissions
# (Memory resources don't have a simple one-line CLI delete; use the
# MemoryClient.delete_memory() SDK call or the AWS Console.)
```
